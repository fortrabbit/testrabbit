How to use this — testing NEW vs OLD, and what to expect

The question: does paying for a bigger PHP plan do anything? A plan gives you two things, both probed here — more PHP processes (concurrency) and more memory. Whether extra processes become extra throughput is the open question; that part needs the k6 arrival test. This page is the fast, visual leading indicator.

Run it on each platform. The page tests whichever host serves it — deploy to both apps and open each:

  • NEW — https://testrabbit.frb.one/load.html
  • OLD — https://testrabbit-uni.frb.io/load.html

Per platform, at each plan tier (rescale in the dashboard between runs, then reload):

  1. Note memory_limit (header above, or the info preset).
  2. Concurrency: N=20, wait=1000 → record the wave-1 count (≈ PHP processes).
  3. Memory ceiling: run it → record the ceiling.
  4. Bump the plan up, reload, repeat. Then compare NEW vs OLD at matched plans.

What we expect to find:

  • Concurrency — wave-1 should equal the plan's process count: advertised XS/SM/MD=2, LG=4, XL=6, 2XL=8. So expect it flat across the three smallest tiers, then rising. If it does not rise where it should, concurrency is capped on the platform — a real finding (→ MR-126).
  • Memory ceiling ≈ memory_limit. It grows with the plan only if the plan actually raises memory_limit — an open question this settles per tier.
  • NEW vs OLD — compare process count + ceiling at matched plans. NEW has historically shown lower capacity and a small per-op tax; watch whether its per-plan processes/memory match OLD's.
  • The catch — more processes only become more throughput if requests wait (I/O). That is what the k6 B0 arrival test measures; this page confirms the processes/memory are (or aren't) there to begin with.

Concurrency — fire N parallel requests

Each request just waits (holds no CPU). If the plan runs P PHP processes, ~P finish in the first wave (≈ the wait time); the rest queue into later waves. That wave-1 count ≈ the plan's concurrency. Expect wave-1 ≈ the plan's process count (2/2/2/4/6/8 for XS→2XL); flat across the smallest tiers, then rising.

Memory ceiling (effect A)

Requests increasing mb until one exceeds memory_limit and returns HTTP 500. The highest size that still returns 200 is the ceiling — it should rise with the plan iff memory_limit scales.
